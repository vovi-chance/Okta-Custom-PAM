Okta Workflows — JIT Admin Access Visual Guide

A card-by-card visual reference for building the 6 Okta Workflow flows that power the Just-In-Time Admin Access portal. Each card below mirrors an action card in the Okta Workflows designer.

Flow Inventory (Build in This Order)

  1. 1.4 Helper – JIT Admin Expire (Helper)
  2. 1.3b Helper – JIT Safety Net Check (Helper)
  3. 1.3a Schedule – JIT Safety Net Poller (Scheduled)
  4. 1.2 Helper – Wait & Suspend (Helper)
  5. 1.1 Helper – JIT-Admin-Approve (Helper)
  6. 1.0 Main – JIT Admin Activate (API Endpoint)

Quick-Start Prerequisites

  1. Create a named Okta Connection in Workflows (e.g. "Okta – YourOrg").
  2. Set up Linked Objects in Okta (standard user → admin account).
  3. Create a JIT Admin Group — note its Group ID.
  4. Add a JIT Expiration custom profile attribute (text/datetime).
  5. Create the Audit Table in Okta Workflows (see schema below).
  6. Ensure approvers have Okta Verify push enrolled.

Build Instructions

  1. Create a new Helper flow named 1.4 Helper – JIT Admin Expire.
  2. Add the 5 inputs listed above (AdminID, tableRowId, requestorId, source, requestorName).
  3. Step 1: Drag an Okta → Read User card. Map AdminID to the ID field.

  6. FALSE path: Add a Return Error card with a descriptive message.

1.3b Helper – JIT Safety Net Check

Build Instructions

  1. Create a Helper flow named 1.3b Helper – JIT Safety Net Check.
  2. Add the 6 inputs above.
  3. Step 1: Date & Time → Difference. End = expirationDateTime, Start = currentDateTime.
  4. Step 2: If/Else — minutes ≤ 0. FALSE → Return Error "Not yet expired".
  5. Step 3 (TRUE): Okta → Read User with AdminID.
  6. Step 4: Another If/Else — Status == "ACTIVE".
  7. TRUE → Call Flow → 1.4 Expire with source = "schedule".
  8. FALSE → Update Row — set status = "processed".

Build Instructions

  1. Create a Scheduled flow named 1.3a Schedule – JIT Safety Net Poller.
  2. Set the schedule to every 5–15 minutes. Keep it OFF until testing is complete.
  3. Step 1: Tables → Search Rows. Filter: status = "pending".
  4. Step 2: List → For Each. Select 1.3b Safety Net Check. Set concurrency to 1. Map the 6 fields from each row.

Build Instructions

  1. Create a new API Endpoint flow named 1.0 Main – JIT Admin Activate. Turn it ON.
  2. The trigger card auto-creates from the HTTP POST body. Define the 10 inputs in the table above.
  3. Steps 1–2: Read User + Concatenate first/last name.
  4. Step 3: If/Else — is requestor ACTIVE? FALSE → Return Error.
  5. Steps 4–5: Get Linked Object → check Admin ID exists. FALSE → Return Error.
  6. Steps 6–7: Read Admin User → check NOT already ACTIVE/PROVISIONED. FALSE → return message.
  7. Step 8: Call Flow → 1.1 Approve. Pass all required fields.
  8. Step 9: Check approvalResult. FALSE → flow ends.
  9. Steps 10–11: Search pending rows (context) → Return success to API caller immediately.
  10. Steps 13–14: Unsuspend Admin → Add to JIT Admin Group.
  11. Steps 15–16: Calculate expiration datetime → Create audit table row.
  12. Step 17: Update admin profile with JIT Expiration.
  13. Step 12: Call Flow Async → 1.2 Wait & Suspend. This runs in the background.
  14. Note: Create the table row (Step 16) before the async call so tableRowId is available.

Audit Table Schema

Reference

Create this table in Okta Workflows before building any flows. All flows read from and write to this single table.

ColumnTypeDescription
AdminIDTextOkta ID of the admin account
requestorIdTextOkta ID of the requestor
requestorEmailTextRequestor's email
requestorNameTextRequestor's display name
durationMinutesNumberRequested duration in minutes
expirationDateTimeText/DateTimeWhen access should end
sourceTextWhich system/flow created the record
correlationIdTextRequest tracking ID from the portal
createdAtTextWhen the record was created
notesTextFree-text notes
statusText"pending" while active, "processed" after expiration
processedSuspensionTimestampTextWhen the account was actually suspended

End-to-End Flow Summary

API Request → 1.0 Main – JIT Admin Activate
  ├─ Read requestor profile
  ├─ Build display name
  ├─ [CHECK] Requestor account is ACTIVE?
  │     No  → Return error "Not Active"
  ├─ Get linked admin account ID
  ├─ [CHECK] Admin account is linked?
  │     No  → Return error "No Admin Account"
  ├─ Read admin account profile
  ├─ [CHECK] Admin is NOT already elevated?
  │     Already elevated → Return "Admin account already active"
  ├─ Call 1.1 Helper – JIT-Admin-Approve
  │     ├─ [CHECK] requestType == "emergency"?
  │     │     Yes → Look up manager → MFA push to MANAGER
  │     │     No  → MFA push to REQUESTOR (self-approval)
  │     ├─ Issue MFA Challenge
  │     ├─ Poll MFA Status (loops until result)
  │     └─ Return approvalResult (True or False)
  ├─ [CHECK] Approved?
  │     No  → Flow ends (access denied)
  ├─ Return success to API caller (immediate)
  ├─ Unsuspend admin account
  ├─ Add admin to privileged group
  ├─ Calculate expiration datetime
  ├─ Write audit table row
  ├─ Update admin profile with expiration
  └─ Start async → 1.2 Helper – Wait & Suspend
        ├─ Wait [durationMinutes]
        └─ Call 1.4 Helper – JIT Admin Expire
              ├─ [CHECK] Still ACTIVE?
              │     Yes → Suspend + Remove from group + Update table
              │     No  → Return error (already handled)
              └─ Return "Success"

Scheduled Safety Net (every 5–15 min):
1.3a Schedule – JIT Safety Net Poller
  ├─ Search table: status = "pending"
  └─ For Each row → 1.3b Helper – JIT Safety Net Check
        ├─ Calculate minutes remaining
        ├─ [CHECK] Expired? (minutes ≤ 0)
        │     No  → Skip
        ├─ [CHECK] Admin still ACTIVE?
        │     Yes → Call 1.4 Expire
        │     No  → Mark row "processed"
